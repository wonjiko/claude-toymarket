# 레포 방향성 원칙 문서 설계

## 요약

이 레포에서 만드는 모든 결과물이 일관되게 지켜야 할 원칙을 담은 별도 문서를 만든다. README는 정보 전달이 목적이고, 이 문서는 작업 결과물의 일관성이 목적이라 역할이 다르다.

## 동기

특정 사고나 계기 없이, 레포가 더 커지기 전에 방향을 미리 세워두기 위해 만든다.

## 스코프

- 다루는 내용: 품질/설계 기준, 톤/스타일, 구조/컨벤션을 소재로 삼되, 목차를 이 세 축으로 고정하지 않는다. 실제로 저장소에서 판단이 필요한 지점을 기준으로 항목을 구성한다.
- 다루지 않는 내용: 플러그인 디렉토리 구조나 frontmatter 필드처럼 자동으로 검증되는 것은 아래 원칙 4에 따라 이 문서에 반복하지 않는다.
- 독립성 제약: 문서 안의 어떤 문장도 특정 스킬 이름이나 파일 이름에 의존하지 않는다. 그 대상이 사라지거나 이름이 바뀌어도 문장 자체는 그대로 유효해야 한다. 행위나 역할로만 설명한다.
- 소비 방식: Claude/Codex가 작업 시 CLAUDE.md, AGENTS.md와 같은 층위에서 항상 참고하는 문서를 목표로 한다. 다만 두 파일에서 이 문서를 실제로 가리키게 만드는 작업, 그리고 README와 CLAUDE.md에 있는 기존 "원칙"/"규칙" 섹션을 손보는 작업은 이번 설계 범위에 넣지 않는다.

## 검토한 대안

- **A. 원칙 중심** — 핵심 원칙 3~5개만 뽑아 근거를 붙이는 방식. 판단이 필요한 순간엔 여전히 추상적이라 채택하지 않았다.
- **B. 축별 가이드 — 채택** — 품질/설계, 톤, 구조 축을 소재로 삼되 목차는 그 축으로 고정하지 않고, 실제 판단이 필요한 지점마다 원칙을 하나씩 두어 지시와 근거를 한 항목 안에 담는 방식. 브로드한 원칙과 구체적 근거가 공존해야 한다는 요구와 가장 잘 맞는다.
- **C. 결정 기록형** — "상황 → 대안 → 결정 → 이유"를 날짜별로 쌓는 ADR 스타일. 근거는 남지만 전체 방향을 한눈에 파악하기 어려워 채택하지 않았다.

## 원칙 — 최종본

1. 되돌리기 어렵거나 외부에 흔적을 남기는 작업에는 검증 단계나 사용자 확인을 넣고, 한 줄 찍고 끝나는 작업에는 넣지 마세요. 되돌릴 수 없는 실수는 결국 사람이 직접 치워야 하니까요.
2. 모든 컴포넌트는 왜 존재하는지와 언제 쓰면 안 되는지를 스스로 말하게 하세요. 그래야 나중에 이 도구를 지금 써도 되는지 바로 판단할 수 있습니다.
3. 담백하고 직접적으로 쓰세요. 마케팅 언어나 과장된 수사는 쓰지 말고, 결론을 먼저 쓰고 설명은 뒤에 붙이세요. 같은 말이면 짧은 쪽을 고르세요. 읽는 사람이 이해하는 데 시간이 오래 걸릴수록 실제로 읽힐 확률은 줄어듭니다.
4. 기계적으로 검증되는 내용은 문서에 반복하지 마세요. 코드와 문서가 같은 사실을 따로 들고 있으면 둘 중 하나가 먼저 낡습니다.
5. 하나의 단위가 서로 무관한 여러 관심사를 담기 시작하면 쪼개세요. 관심사가 섞이면 하나를 고치다가 다른 하나를 깨뜨리기 쉬워집니다.
